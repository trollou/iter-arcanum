# Architecture du code

Fiche d'orientation pour ne pas réexplorer le code à chaque spec : où vit quoi, et la recette pour ajouter une action, un événement
ou un élément d'écran. Les principes sont dans `CLAUDE.md` et les ADR (`docs/decisions/`) ; cette fiche ne décrit que l'état actuel.

**À tenir à jour** : toute PR qui ajoute un module, un type clé ou change une recette met cette fiche à jour dans la même PR.
Dernière mise à jour : spec 082, crates renommées `arcanum-*` (anciennement `mk-*`), exécutable `iter-arcanum`.

## Crates

```
arcanum-ui ──► arcanum-core
   ├────► arcanum-i18n
   ├────► arcanum-audio ──► arcanum-core
   └────► arcanum-persistance ──► arcanum-core
```

|---|---|---|

Module `preferences` : fichier des préférences (spec 080), volumes compris (spec 081). | `serde`, `serde_json`, `thiserror`, `log` |
| `arcanum-audio` | Son (spec 081, ADR 0010) : directeur pur, banque de sons, lecteurs (Kira ou muet). Écoute la partie, ne la change jamais. | `kira` (sans options par défaut : `cpal`, `ogg`, `vorbis`), `thiserror`, `log` |

`arcanum-players` n'existe pas encore. Règles propres à chaque crate : `.claude/rules/`.

## arcanum-core

Tous les types publics sont réexportés par `lib.rs` : `use arcanum_core::{…}` suffit, les modules sont privés.

### Le cycle d'une décision (ADR 0001 et 0002)

```
GameRunner::step()
  ├─ pending_decision(&state)        qui doit choisir ? (None = partie finie)
  ├─ view(&state, joueur)            ce qu'il a le droit de voir
  ├─ legal_actions(&state, joueur)   liste exhaustive
  ├─ Player::request / poll          le joueur choisit un index (sans bloquer)
  ├─ decide(&state, joueur, &action, &mut rngs) -> Vec<Event>  valide, résout le hasard
  └─ apply(state, &event)            pour chaque événement : pur, infaillible, journalisé
```

### Recette : ajouter une action

1. Variante dans `Action` (`action.rs`), commentée avec la spec.
2. Énumération dans `available_actions` (`engine/legal/mod.rs`, la fonction `*_actions` dans le fichier de son thème) : ordre stable et documenté, l'ordre fait partie du contrat (les index
   choisis par les joueurs en dépendent). Choix de fin de tour d'abord : `ChooseCrystalColor` (spec 044), `TakeArtifact` (spec 041), `TakeSpell` (spec 043), `ChooseSkill` (spec 051), `GainAdvancedAction`, puis `TakeUnitReward` et `DeclineUnitReward` (spec 045).
   Hors combat : `PlunderVillage` (spec 041), cartes, unités (`ActivateUnit`), soins (`SpendHealing`), `MoveHero`, `FollowRoute`
   (spec 036 ; vers un site fortifié non conquis : assaut, spec 043), `Explore`, `Interact` (spec 040), `BurnMonastery` (spec 041), `EnterAdventureSite` (spec 044, ruines comprises), `PayAltarTribute` (spec 045), défis, fins de tour (pour chaque défausse : sans `glade`, puis main, puis défausse, spec 044), `AnnounceEndOfRound` ; en
   interaction : cartes, unités, soins, recrutement, `BuyAdvancedAction`, `BuySpell` (spec 043), `BuyHealing` (spec 041), fin du tour ; en combat :
   cartes, unités, cibles, assignation des dégâts (spec 042), phases. Une action insérée décale les index des suivantes : les tests et joueurs choisissent par valeur.
3. Variante dans l'aiguillage de `decide` (`engine/decide/mod.rs`) et bras dans la fonction `<thème>_actions` du thème qui convient de `engine/decide/` (les événements longs à produire dans le thème qui convient de `engine/events/` ; un bras de plus de ~30 lignes devient une fonction `<action>_events` du même fichier ; un `return Ok` y sort de la fonction du thème, et les passes finales de `decide` s'appliquent toujours : issues privées 321 et 343) : produit les événements, tire le hasard dans `rngs.rng(usage)` (jamais ailleurs) ; un nouveau tirage qui n'appartient à aucun usage existant ajoute un `RngUsage` avec un numéro de flux libre (ADR 0007).
4. Tests dans `crates/arcanum-core/tests/<notion>.rs` : action légale ou non, événements produits, état après `apply`.
5. Côté UI : voir « ajouter une commande » plus bas.

### Recette : ajouter un événement

1. Variante dans `Event` **et** dans `PlayerEvent` (`event/mod.rs`), rangée dans un thème par `Event::theme` (exhaustif : le compilateur le réclame), plus sa branche dans la fonction `filter` du fichier de ce thème (`event/<thème>.rs`) : décider ce qu'un autre
   joueur en voit (le filtrage est testé).
2. Branche dans `apply` : la variante dans le thème qui convient de l'aiguillage `apply_event` (`engine/apply/mod.rs`, exhaustif : le compilateur le réclame), le bras dans la fonction `<thème>_event` de son fichier (`engine/apply/<thème>.rs` ; un bras de plus de ~30 lignes devient une fonction `apply_<événement>(state, …)` dans le même fichier) : pure, infaillible ; un événement sans objet ne change rien (pas de panique). Branche
   dans la fonction `blocks_undo` du même fichier `event/<thème>.rs` : point de non-retour ou non (spec 024) ; un oubli y tombe sur le bras `unreachable!`, qu'un test de l'événement fait paniquer.
   Conséquence pour les tests : `apply` ignore en silence un événement sans objet (recruter une unité absente de l'offre,
   gagner une carte absente de son offre, soigner une unité intacte…), et aucun fait du tour n'en naît. Un décor de test
   doit donc rendre l'événement possible (carte ou unité dans l'offre, unité blessée avant de la soigner) ; sinon le test
   reste rouge pour une mauvaise raison (bilan de la spec 073, issue privée 176).
3. Nouveau champ d'état : dans `GameState` ou `PlayerState`, avec un accesseur public sur `GameState`, puis dans `PlayerView` et
   `view` s'il est visible du joueur. Les tests qui construisent un `PlayerView` champ par champ (arcanum-ui) sont à compléter.
4. `Event` et tout ce qu'il porte dérivent `serde::Serialize` et `Deserialize` (sauvegardes, spec 024) : un nouveau type porté par
   un événement aussi. `Effect` a sa forme complète ; la forme courte des fichiers de contenu passe par `effects_from_text`.
5. Changer un événement existant, ou un type qu'il porte (spec #52, ADR 0001) : le test `format` d'arcanum-persistance
   compare l'empreinte du format à `tests/format/sauvegarde.yaml`. **Compatible** (variante ajoutée, champ ajouté avec
   `#[serde(default)]` qui redonne l'ancien sens) : régénérer l'empreinte
   (`ARCANUM_REGENERER_DOCS=1 cargo test -p arcanum-persistance --test format`). **Incompatible** (champ ou variante
   renommé ou retiré, champ obligatoire ajouté, type changé, usage de générateur renommé, ou nouveau sens donné par
   `apply` à un événement existant, que l'empreinte ne voit pas) : `EVENT_FORMAT_VERSION` passe à
   `PREVIOUS_RELEASE_FORMAT + 1` s'il ne l'a pas déjà fait depuis la dernière release (une fois par cycle), et la
   migration de ce format (`MIGRATIONS`, `src/migration.rs`, une fonction pure sur le JSON entier) est écrite ou
   complétée, avec son test ; `diff tests/format/v<X.Y.Z>.yaml tests/format/sauvegarde.yaml` liste ce qui a changé depuis
   une version gardée. Toute PR qui change le bras d'`apply` d'un événement existant le dit en une ligne : « Sens
   d'`apply` changé : non » ou « oui : <événements> ».

### Recette : ajouter du contenu (carte, tuile, scénario)

Les valeurs vont dans un fichier RON de `crates/arcanum-core/content/` (spec 029, ADR 0005) ; identifiants et mécaniques restent en Rust.

1. Identifiant : variante de l'enum (`BasicAction`, `Hero`…), `#[derive(Deserialize)]` ; libellé (`label_key()`) dans tous les
   `assets/i18n/*.json`, terme dans `docs/glossaire.md`.
2. Définition dans le fichier de contenu de la famille. Un effet que le moteur ne sait pas jouer est une variante de `Effect` (et
   de sa forme écrite `EffectText` dans `content.rs`) apportée par la spec qui en a besoin.
3. Nouvelle famille : un fichier `content/<famille>.ron`, un champ de `ContentSources`, sa lecture et sa validation dans
   `GameContent::parse` (identifiant manquant, en double, références vers les autres fichiers), testées dans
   `crates/arcanum-core/tests/contenu_en_donnees.rs` sur des textes de test.
4. Un scénario reste une valeur Rust de `Scenario`, avec un test de mise en place : ses règles spéciales sont du code.

### Recette : une carte qui change une règle pour le tour (effet en cours)

1. Si une sorte de `ModifierKind` (`modifier.rs`) fait déjà ce que dit la carte, seulement des données : l'option s'écrit
   `With(effet, [modificateurs])` dans `content/advanced_actions.ron` (ou `units.ron` pour une capacité), ADR 0008.
2. Sinon, une sorte paramétrée de plus, et la règle qui la consulte : le déplacement (`MoveRules::new`), la jouabilité
   (`PlayMoment::serves`, sinon la carte ne se joue que de côté), le combat ou la fin du tour (`decide` d'`EndTurn`).
3. Une durée autre que le tour : variante de `ModifierDuration` et l'événement qui la clôt dans `apply`.

### Recette : ajouter un élément aux panneaux

1. Champ dans `GameScreen` (`screen/mod.rs`), calculé dans `game_screen` (ou dans le sous-module de sa zone) depuis la **vue** seule (jamais l'état complet), textes via
   le catalogue.
2. Clés dans `assets/i18n/*.json`.
3. Dessin dans `app/side_panel.rs` (panneau de droite) ou `app/bottom_panel.rs` (panneau du bas, cartes et bandeau du choix) (petits widgets réutilisables dans `app/widgets.rs`).
4. Tests dans `crates/arcanum-ui/tests/<notion>.rs` sur `game_screen` (sans fenêtre) ; vérification à l'œil avec
   `scripts/verif-manuelle.sh` (voir `docs/verification-manuelle.md`).
5. Quand un dessin change de place, retirer l'ancien champ : chaque champ de `GameScreen` est lu par `app/`, et un test lit ce
   que l'écran dessine, sinon il passe sans rien vérifier (issue privée 259 ; aides `end_turn_button`, `announce_button`,
   `combat_labels` de `tests/support/mod.rs`).

### Recette : ajouter une commande ou un raccourci

1. Le bouton porte une `Command` ; le plus souvent `Command::Play(index)` avec l'index de l'action dans les actions légales.
2. Un choix en plusieurs clics (ex. cocher des cartes) est un `ScreenMode` : le moteur ne reçoit que l'action complète.
3. Raccourci : variante de `Shortcut`, ligne de `KEY_BINDINGS` (`keys.rs`) lue par `app/mod.rs`, exécutée par `GameSession::shortcut` (testable sans
   egui). Déclarer la touche dans `docs/raccourcis.md`.
4. Le bouton montre sa touche en infobulle (spec 071) : champ `shortcut` rempli par `shortcut_label` (ou `take_label_of` pour un choix
   numéroté), dessiné par `shortcut_button`. Une valeur de jeu s'affiche en icône (`icon_value`, dessinée par `app/icons.rs`).

## arcanum-audio

Le son écoute la partie et ne décide rien (spec 081, ADR 0010). Règles : `.claude/rules/arcanum-audio.md`.

| Module | Contenu |
|---|---|
| `lib.rs` | Types : `Music`, `Ambience`, `Cue` (les dix-neuf effets, `Cue::ALL` dans l'ordre de priorité), `SoundCategory`, `SoundSituation` (`Title`, `Exploration`, `Combat`, `GameOver` avec `Outcome`), `Fade`, `AudioCommand`. |
| `director.rs` | `AudioDirector` (pur, testé) : `update(situation, &[PlayerEvent])` rend les ordres d'une image (musique et ambiance à chaque changement de situation, fondus de `fade(depuis, vers)` ; effets une fois par image, les pas un par case espacés de `step_interval`, quatre au plus) ; `preview(catégorie)` (échantillon du curseur tenu) ; `set_volume`. |
| `cues.rs` | `cue_of(événement, situation)` : la table des effets de la spec (joueur `SOLO` seul, sauf `GameEnded`). |
| `bank.rs` | `SoundBank::scan(dossier)` : `music/`, `ambience/`, `effects/` (variantes `_N`, à tour de rôle par le `nth` du directeur) ; un fichier manquant n'est pas une erreur (un `warn` par effet). |
| `licenses.rs` | `check_licenses` : chaque `.ogg` de `assets/sounds/` a sa ligne dans `LICENSES.md`, licence permise (`FREE_LICENSES`, puis `NON_COMMERCIAL_LICENSES` comptées à part). |
| `player.rs` | Trait `AudioPlayer` (`execute(&AudioCommand)`), `SilentPlayer`, `KiraPlayer` (une piste par type de son sous la piste principale, musique et ambiance en flux, effets en mémoire ; fichier illisible : un `warn`, une fois). `KiraPlayer` n'a pas de test : vérification à l'oreille. |

Branchement dans arcanum-ui : `ClientSession::take_heard_events` (événements filtrés pour `SOLO`, apparus depuis l'appel d'avant ;
rien après un retour en arrière ou un chargement) et `sound_situation` (`sound.rs`) ; `IterArcanumApp::logic` appelle
`director.update` après `run_frame` et passe les ordres au lecteur. Volumes : `Command::SetVolume` (pendant le glissé) et
`SaveVolumes` (au lâcher, ou 1 s après le dernier changement au clavier), demandes `WindowRequest::Volumes` et `Preview`.

### Recette : ajouter un effet sonore

1. La spec dit l'événement déclencheur et sa place dans l'ordre de priorité.
2. Une variante de `Cue` (et dans `Cue::ALL`, `file_stem`), sa ligne dans `cue_of` (`cues.rs`), un test dans
   `crates/arcanum-audio/tests/effets.rs`.
3. Le fichier `assets/sounds/effects/<nom>.ogg` (Ogg Vorbis mono), choisi avec Mathieu sur une planche d'écoute
   (`scripts/sons/planche.py`, README à côté) et sa ligne dans `assets/sounds/LICENSES.md` : les tests
   `every_sound_has_a_permitted_license` et `every_cue_has_a_sound_within_budget` le vérifient.

## arcanum-persistance

Ne choisit pas le dossier (arcanum-ui le fait) et n'a pas d'horloge (la date du résumé est donnée par l'appelant).
`SaveGame::from_runner(&runner, date)` puis `save(dossier, nom, &game)` (suffixe `-2`… si le nom est pris) ou `save_auto` (`auto.json`) ;
`load(chemin)?.resume(joueurs)` rejoue le journal par `GameRunner::resume`. `list(dossier)` : automatique en tête, plus récentes
ensuite, illisibles à la fin. Version vérifiée avant les événements. Module `migration` (spec #52) : `Formats` (plus ancien
format gardé, format courant, chaîne `MIGRATIONS` ; `Formats::SUPPORTED` pour les vrais, `load_with` et `list_with` pour ceux
d'un test), `OLDEST_SUPPORTED_FORMAT`, `PREVIOUS_RELEASE_FORMAT` ; une sauvegarde d'un format gardé plus ancien est migrée
en mémoire, une plus récente est `NewerVersion`, une trop ancienne `TooOld`, une migration ratée `NotMigratable`. Tests :
`crates/arcanum-persistance/tests/sauvegarde.rs` et `migration.rs` (chaîne de test), dossiers temporaires (`tempfile`) ;
`temoins.rs` (sauvegardes des versions gardées, `tests/temoins/v<X.Y.Z>/`, jamais régénérées) ; `format.rs` (empreinte du
format par `serde-reflection`, `tests/format/sauvegarde.yaml` et une empreinte figée `v<X.Y.Z>.yaml` par version gardée).

Module `preferences` (spec 080) : `Preferences` (langue, plein écran au lancement, `Volumes` de la spec 081, `animations` de la spec #5, vrai par défaut ; `Default`), `load(chemin)` tolérant (champ
absent : défaut ; champ inconnu : ignoré ; autre `version` : `warn`, lu quand même ; fichier absent : `PreferencesError::Missing`)
et `save(chemin, &préférences)`, qui crée le dossier et écrit un fichier temporaire renommé à sa place. Tests :
`crates/arcanum-persistance/tests/preferences.rs`, logs par le `support/logs.rs` d'arcanum-ui (issue privée 358).
